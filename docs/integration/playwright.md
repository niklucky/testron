# Playwright integration

Testron supports portable tests and CI catalogue tests. Both keep a stable test ID
and can report local/CI results. Use `testron pull` to generate typed suite references.

```ts
import { test, expect } from '@playwright/test';
import { testron, suites } from '../../testron.generated';

test(
  'Dashboard is available',
  testron({
    suite: suites.Dashboard,
    publish: true,
    execution: 'ci-and-testron',
    description: 'A visitor can open the dashboard.',
    steps: ['Open dashboard', 'Verify the Dashboard heading'],
  }),
  async ({ page }) => {
    await page.goto('/dashboard');
    await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();
  },
);
```

## Portable tests

Standalone tests marked `ci-and-testron` are synchronized as editable Playwright
source and steps. They can run in Testron after assigning an environment, with an
optional authentication profile. Relative navigation uses the selected environment.
Existing environment/profile assignments survive a pull/edit/push round trip.
New tests require explicit environmentIds in testron.config.ts or an assignment in
the UI; publishing never automatically chooses a target.

The existing structured runner supports the actions and assertions generated by
the editor. There is no new authoring linter or sophisticated portability checker.
Agents should use the skill at https://testron.dev/agents/SKILL.md to review source.
Unsupported arbitrary code stays visible and may produce a runner error.

Normal helper imports, custom fixtures, and top-level setup make a test catalogue-only.
The generated testron.generated and testron.fixture modules are integration adapters
and do not cause that downgrade. Push reports any downgrade in its output.

## CI catalogue tests

Use `execution: 'ci-only'` for tests that rely on disposable databases, seeded data,
helpers, or a prepared repository environment. This is the default execution mode.
Supply a human-readable title, description and steps for QA. The title comes from
the Playwright test; absent descriptions default to that title, and absent steps
use the existing parser's readable projection. Agents should write meaningful
scenario steps explicitly for complex tests.

Only selected spec files and the test's source excerpt are published, without
helpers, configuration files, credentials, or dependency bundles. Catalogue tests
are read-only in the UI and cannot be run or scheduled on Testron. Their local/CI
runs appear when the reporter is configured.

## Publication and identity

Publication is opt-in with `publish: true`. Suite, publication, execution, description,
and scenario-step annotations can be supplied on a describe; nearest values win.
Use `publish: false` to exclude a test in a published group. `-f` narrows selection
but does not opt tests in. Whole selected spec files are synchronized: unpublished
tests sharing a file may still be visible in its source, but receive no catalogue entry.

Preserve IDs when renaming or moving cases. New cases need new IDs. The CLI assigns
missing IDs to ordinary declarations; parameterized cases need explicit IDs per row.
Do not put a test ID on a describe. Suite keys survive display-name changes.
Unassigned tests pulled from Testron can keep their existing unassigned suite.

Removing publication stops future uploads; it does not delete the remote record.
Push a CI-only update to disable remote execution while retaining history.

## Pull and run locally

`testron pull --test <id>` exports an editable test with its ID and metadata.
Set importDir in testron.config.ts to a path collected by your Playwright projects
(default tests/testron). Confirm discovery with `playwright test --list`.

The generated local fixture requires TESTRON_BASE_URL. For a test with a Testron
profile, set TESTRON_STORAGE_STATE to a file from your local/CI login setup. Variables
referenced by test steps also come from the local environment. Remote credentials
are never exported. A missing local target/authentication setting fails explicitly.

```sh
TESTRON_BASE_URL=http://127.0.0.1:3000 \
TESTRON_STORAGE_STATE=tests/e2e/.auth/local.json \
npx playwright test tests/testron/<test-id>.spec.ts

testron push -f tests/testron/<test-id>.spec.ts --dry-run
testron push -f tests/testron/<test-id>.spec.ts
```

Portable tests stay editable and runnable after push. A helper/setup dependency
turns them into read-only catalogue tests and disables remote runs. Existing
custom-code or multi-origin documents may need manual local-target adaptation on
pull; Testron does not silently discard that behavior.

## Report local and CI results

The Playwright reporter uploads results as tests finish. `testron push` publishes test
source and metadata; it does not upload run results. Tests still run in your existing
local/CI environment with its database, seed data, helpers, and authentication setup.

### Install and configure the reporter

Install `@testron/cli` in the project and make it available in the CI job's dependencies.
For development before a package release, install the built CLI archive, for example
`npm install --save-dev /path/to/testron-cli-0.1.0.tgz`. CI needs access to that archive
through your package distribution or build artifacts; a laptop-only path will not work.

Add the reporter alongside your existing reporters in `playwright.config.ts`:

```ts
reporter: [
  [process.env.CI ? 'line' : 'list'],
  ['html', { open: 'never', outputFolder: 'playwright-report' }],
  ['@testron/cli/reporter'],
],
```

Keep any existing HTML reporter options and CI artifact paths. If the job overrides
reporters with `--reporter`, include `@testron/cli/reporter` in that override too.

Configure these values:

- `server` in `testron.config.ts`: a Testron server reachable from the CI runner.
  `http://127.0.0.1:4477` points at the runner itself, not your laptop. Remote servers
  must use HTTPS. To vary the URL by environment, explicitly read an environment
  variable in the config, such as `server: process.env.TESTRON_SERVER ?? 'http://127.0.0.1:4477'`.
  The CLI does not automatically read TESTRON_SERVER.
- `TESTRON_API_KEY`: a project-scoped API key stored as a masked CI secret. Create
  one from an authenticated developer checkout with `testron key create --name ci`.
  The CLI saves it in its credential store; transfer it securely to the CI secret
  store, never into committed files or job logs.
- `TESTRON_REPORT_ENVIRONMENT_ID`: the UUID of an environment in the same Testron
  project, for example one named CI. Alternatively set `reportEnvironmentId` in
  `testron.config.ts`. This labels results; it does not change the Playwright target
  or grant execution permission on Testron. CI-only tests stay CI-only.

Local reporting can also use the CLI credential store. Run all commands from the
project root containing `testron.config.ts`.

### Establish the revision baseline

Publish the selected tests before the pipeline runs. Commit their stable `testron.id`
annotations, `testron.config.ts` (including the same repositoryId), and generated
suite references. Tests without a `testron.id` are skipped by the reporter.

On a fresh CI checkout, pull the published source for the suites being reported:

```sh
npx testron pull --tests --suite Authentication
npx testron pull --tests --suite Files
npx testron pull --tests --suite Organizations
```

These are example suite code keys; replace them with yours. Use `--test <uuid>` to
select an individual test instead. Selecting suites avoids importing unrelated tests.
The pull checks local source against the published files and records synchronized
revisions in `.testron/state.json`. Plain `testron pull` only refreshes the catalog
and does not establish this baseline on a fresh checkout. A successful push also
establishes a baseline in the checkout where it runs.

Keep the CI checkout aligned with the published source. If pull reports a conflict,
reconcile and publish the intended test revision; do not overwrite the checkout or
push automatically just to bypass the conflict. Keep `.testron/state.json` local to
the checkout instead of committing it or copying another project's state.

### GitLab CI example

After installing the package and setting the CI variables, add the pulls before your
existing Playwright command. For a Bun project with a `test:e2e` script, the existing
E2E job's script can be:

```yaml
script:
  - bunx testron pull --tests --suite Authentication
  - bunx testron pull --tests --suite Files
  - bunx testron pull --tests --suite Organizations
  - bun run test:e2e
```

Keep the job's current image, database/setup services, and artifact configuration.
There is no separate result-upload command after the test run. GitLab sets `CI`, so
these reports are labelled CI; executions without `CI` are labelled repository-local.

### Results and current limits

QA sees status, duration, errors, synchronized revision, source hash, Playwright
project, and retry in the test's Runs column. The source hash identifies the code
actually run, even when it differs from the synchronized revision. Each completed
attempt is reported; skipped or interrupted tests are currently shown as cancelled.

Missing configuration, missing synchronized revisions, and upload failures are
reported explicitly and cause the reporter to fail the run. Do not treat a test
failure as an upload failure: a failing test can still have a successfully reported
result. Abruptly terminated jobs may leave results unreported.

Screenshots, videos, and Playwright traces from local/CI runs are not uploaded by
this reporter yet. Keep them in your existing CI artifacts.
